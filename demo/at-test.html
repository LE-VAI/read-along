Screen reader test — read-along live region

A manual accessibility test. It answers one question: does a screen reader actually announce the read-along status messages, and does it do so once per change? Nothing on this page passes or fails on its own — only what you hear counts.

Before you start. Turn your screen reader on before loading this page, so it observes the live region from the beginning.

  • NVDA: start NVDA, then open this page. Speech viewer (NVDA+Alt+N → Tools → Speech Viewer) makes the result unambiguous — a message either appears there or it does not.
  • Use the real browser, not a preview pane. A PDF or in-editor preview of this page will not run the script.

The component under test

Play it with NVDA+Space on the Play button, or click it if you are testing one-handed. The buttons are real buttons and are reachable by Tab.

Read-along announces what it is doing. The words highlight as they are spoken, one at a time, so a reader can follow the sound with their eyes. This paragraph is long enough that pausing mid-sentence is easy to do, and long enough that the announcement has to happen while speech is still running rather than only at the end.

If the component did not render, the module did not load — serve this page over http rather than opening the file directly.

Checks

1 Press Play. You should hear the text read aloud and a status message announcing that playback started.

Why it matters: this is the baseline. If the first announcement is silent, every later one will be too, and the region is the problem rather than the change-detection.

2 Press Pause, then press Play again, then Pause once more. Each pause should announce — including the second one, which repeats the same word as the first.

Why it matters: this is the exact failure the clear-then-set exists to prevent. A live region announces a change, and assigning an identical string produces no change — so a naive implementation goes silent on every repeated message. A user cannot tell the difference between "the tool ignored me" and "the tool is broken."

3 Press Play and let it finish without touching anything. You should hear a completion message when it ends.

Why it matters: an ending nobody announces is a user waiting for something that already happened.

4 Press Play, then Restart while it is speaking. You should hear the restart announced, and it should not announce twice for one press.

Why it matters: restart stops and starts in one action, so a double announcement here means the region is firing on both halves of a single user intent.

5 Change the Speed dropdown while playing. Playback rate should change and the current word should keep highlighting without skipping or stalling.

Why it matters: not a live-region check. This is the timing path — a rate change mid-utterance is where a sync engine drifts, and a screen reader user is listening while watching nothing, so a stall is total.

6 Press Tab from the top of the page and walk forward through the read-along controls. Every control should be reachable and should say what it does — not just "button".

Why it matters: the shadow DOM hides nothing from a keyboard or a screen reader only if the internals are marked up correctly. A control that announces as "button" with no name is unusable without sight.

The baseline that makes this meaningful

The same region is duplicated below outside any shadow root. If this one announces and the component's did not, the shadow DOM is conclusively the cause — which is the difference between "a screen reader bug we cannot fix" and "a bug in our markup that we can".

Press the button twice. The second press repeats the same text, so it tests the identical-string behaviour in the light DOM too.
